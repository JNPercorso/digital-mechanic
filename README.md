# Цифровой механик

AI-агент для механика автопарка. Берёт результат акустической проверки двигателя из ML-сервиса, объясняет его простым языком по руководствам производителя со ссылкой на страницу PDF, отвечает на вопросы механика и готовит заявку на дефектовку, которая уходит в ТОиР только по нажатию механика.

Проект хакатона «ИИкузница», задача «Цифровой механик» (ООО «НейроДВС»).

- Стенд: https://digital-mechanic.jnpercorso-card.online
- Интерфейс: веб-приложение для смартфона (устанавливается как приложение, PWA), планшета и компьютера.

## Что умеет

- **Результат диагностики.** Кнопка «Получить результат диагностики»: агент сам вызывает инструменты (результат проверки, поиск по руководству, запчасти узла, черновик заявки) и отвечает в порядке из ТЗ: наблюдения, гипотезы, проверки, возможный ремонт, источник, ограничения.
- **Три исхода проверки.** Норма: короткий ответ. Отклонение: разбор и черновик заявки. Сбой записи: выводов о двигателе и заявки нет, просьба повторить запись.
- **Ссылки только на руководство двигателя этой машины.** Каждая ссылка открывает страницу PDF: картинка страницы и её текст, нужный фрагмент подсвечен.
- **Вопросы механика в чате** своими словами (текстом или голосом): нормативы и порядок работ по руководству, данные машины, история проверок, «стало лучше или хуже», «можно ли выпускать на линию», «покажи заявку». На вопросы не о технике агент вежливо отказывает.
- **Черновик заявки:** неисправность, приоритет с объяснением («Почему»), работы и запчасти из руководства, источники. Механик может изменить приоритет, работы и запчасти; отправка в ТОиР только кнопкой.
- **Низкая точность распознавания:** ниже 0,50 заявка не формируется; от 0,50 до 0,60 и при записи с помехами вывод предварительный, первой работой в заявке идёт повторная проверка, отправка только после явного подтверждения механика.
- **Противоречия в руководствах:** агент показывает обе формулировки со ссылками, отмечает противоречие и рекомендует уточнить у специалиста; в заявке консервативный вариант.
- **Повторяющийся дефект** отмечается в истории проверок и в ответе.
- **Озвучка ответа** голосом на своём сервере (Silero), без отправки текста во внешние сервисы.
- **Диалог по машине** хранится на устройстве механика и очищается, когда в ML-сервис приходит новая запись прослушивания.
- **Панель демонстрации:** выбор устройства, оформление, данные тренда, очистка чатов и списка заявок по всем машинам.

## Как устроено

**Агент выбирает инструменты, а слой проверок кодом гарантирует правила заказчика.**

```
Смартфон механика (веб, PWA)
   |  HTTPS, поток ответа (SSE)
FastAPI ──> агент (GigaChat) ──> инструменты:
   |          результат проверки ......... Mock ML-сервис (заглушка заказчика)
   |          история машины и заявок .... SQLite
   |          поиск по руководствам ...... BM25 по страницам PDF двигателя этой машины
   |          запчасти узла .............. справочник обозначений из руководств
   |          черновик заявки ............ проверки -> Mock ТОиР (по кнопке механика)
   |
   └─ слой проверок кодом (в каждом ответе): ссылки только на найденные страницы руководства
      этого двигателя; страницы про другие модели и оглавления не источник; числа и запрет
      эксплуатации только со ссылкой; строка со ссылкой сверяется с текстом страницы;
      заявка только по странице узла неисправности с дословной цитатой; приоритет считает код;
      сбой записи - без выводов; устройство агента не раскрывается.
```

- **База знаний.** Шесть PDF разобраны постранично (PyMuPDF), страницы-картинки распознаны (Tesseract), таблицы разобраны по строкам («причина - способ устранения»). Карта разделов из оглавлений помечает тип раздела (эксплуатация, ТО, неисправности, ремонт, обкатка, детали), агент видит его у каждого фрагмента.
- **Приоритет заявки** считает код: базовая критичность типа неисправности (F01-F14) плюс-минус один уровень по оценке отклонения. Высокий: дефектовка до выпуска в рейс; средний: на ближайшем ТО, под наблюдением; низкий: проверка на следующей проверке.
- **Модель:** GigaChat-3-Ultra (Сбер), запасная GigaChat-3-Pro; запросы к модели идут через очередь, с повторами. Модель и адреса сервисов меняются в настройках.

## Запуск с нуля

Нужны Python 3.12+ (проверено на 3.12 и 3.14), Windows 11 или Linux. Tesseract (с русским языком) нужен только для распознавания страниц-картинок при сборке базы знаний.

```bash
git clone https://github.com/JNPercorso/digital-mechanic.git
cd digital-mechanic
python -m venv .venv
# Windows: .venv\Scripts\activate    Linux: source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env              # заполнить: GIGACHAT_AUTH_KEY, MATERIALS_URL
```

1. **Ключ GigaChat.** В `.env` указать `GIGACHAT_AUTH_KEY` (ключ авторизации из личного кабинета GigaChat API) и `GIGACHAT_SCOPE`. Сертификат Минцифры (`russian_trusted_root_ca_pem.crt`, https://www.gosuslugi.ru/crt) положить в `certs/`.
2. **Материалы задачи** (руководства и данные заглушек, см. ниже): `python -m app.fetch_materials` скачает их по ссылке из `MATERIALS_URL` и соберёт базу знаний.
3. **Запуск:** `python run.py` поднимает заглушку ML (порт 8001), заглушку ТОиР (8002) и приложение (8000). Открыть http://127.0.0.1:8000.

Озвучка голосом на сервере (необязательно): `pip install torch --index-url https://download.pytorch.org/whl/cpu` и модель Silero v4_ru в кеше torch hub (путь задаётся `TTS_MODEL_PATH`). Без неё ответ озвучивает браузер.

### Стенд

Ubuntu в Рег.облаке (Москва), три службы systemd (приложение и две заглушки), HTTPS через Caddy (`reverse_proxy 127.0.0.1:8000`, сертификат Let's Encrypt). Обновление: `git pull`, при необходимости `python -m app.fetch_materials`, перезапуск служб.

### Настройки (`.env`)

| Переменная | Назначение |
|---|---|
| `MOCK_ML_URL`, `MOCK_TOIR_URL` | адреса ML-сервиса и ТОиР (заглушки заменяются рабочими сервисами по тем же контрактам OpenAPI) |
| `MATERIALS_URL` | ссылка на архив материалов задачи |
| `MANUALS_DIR`, `INDEX_DIR` | где лежат PDF и база знаний |
| `GIGACHAT_AUTH_KEY`, `GIGACHAT_SCOPE`, `GIGACHAT_CA_CERT` | доступ к GigaChat |
| `LLM_MODEL`, `LLM_FALLBACK_MODEL`, `LLM_CONCURRENCY` | модель, запасная модель, число одновременных запросов |
| `TTS_SPEAKER`, `TTS_SAMPLE_RATE` | голос озвучки (eugene, 48 кГц) |

## Материалы задачи (руководства и данные заглушек)

Материалы задачи **не входят в репозиторий** и в историю коммитов (требование организаторов, п. 9.1 Положения):

- PDF заводских руководств по двигателям и поисковый индекс с извлечённым из них текстом;
- данные заглушек: карточки машин с результатами проверок, справочник неисправностей (`mocks/data/*.json`).

Код заглушек ML и ТОиР, их контракты (OpenAPI) и тесты в репозитории есть.

### Загрузка при развёртывании

Ссылка на архив материалов задачи задаётся переменной окружения `MATERIALS_URL` (в `.env`), а не в коде. Команда скачивает архив, раскладывает PDF и данные заглушек и собирает базу знаний:

```bash
python -m app.fetch_materials
```

Поддерживаются прямая ссылка на `.zip`, публичная ссылка Яндекс.Диска (файл или папка) и ссылка Google Drive на файл. Сборка индекса занимает несколько минут.

### Вручную

1. Положите шесть PDF в папку из `MANUALS_DIR` (по умолчанию `manuals/`) под такими именами:

   | Файл | Документ |
   |---|---|
   | `yamz-236_re_2010.pdf` | ЯМЗ-236М2, руководство по эксплуатации 236-3902150-Б РЭ |
   | `yamz-236_rk_2014.pdf` | ЯМЗ-236М2, руководство по ремонту 236.01.01 РК |
   | `yamz-536_re_2016.pdf` | ЯМЗ-536, руководство по эксплуатации 536.3902150 РЭ |
   | `yamz-536_rk_2013.pdf` | ЯМЗ-536, руководство по ремонту 536.01.02 РК |
   | `zmz-5234_rk_2025.pdf` | ЗМЗ-5234.10, руководство по ремонту |
   | `zmz-40904-40905_rk_2025.pdf` | ЗМЗ-40904.10 и ЗМЗ-40905.10, руководство по эксплуатации, ТО и ремонту |

2. Положите данные заглушек (`vehicles.json`, `fault_types.json` из `mock/data` материалов) в `mocks/data/`.
3. Соберите базу знаний: `python -m app.rag build`, затем `python -m app.sections build`.

Соответствие документов и двигателей описано в `app/manuals.py`; чтобы добавить двигатель, достаточно добавить строку туда и пересобрать базу.

## Тесты и проверка качества

| Команда | Что проверяет |
|---|---|
| `pytest tests/test_rules.py` | правила кодом: ссылки всех форматов, пороги точности, приоритет, числа и запреты без ссылки, цитаты, противоречия, запчасти, гипотезы (без модели, доли секунды) |
| `python tests/check_pages.py` | база знаний по всем 1743 страницам: полнота текста, таблицы, подсветка на картинке страницы |
| `python tests/rag_quality.py` | контрольные вопросы с эталоном со страниц руководств (норматив и страница) и вопросы-ловушки |
| `python tests/run_scenarios.py [--all] [--dialogs-all] [--judge]` | прогон на живом приложении: диагностика по всем машинам, диалоги из нескольких реплик вперемешку; полный журнал событий и правил, отчёт; судья-модель оценивает ответы по требованиям ТЗ |
| `python tests/judge_calibration.py` | проверка судьи на заведомо плохих и хороших ответах |
| `python tests/e2e_ui.py` | интерфейс в браузере (Playwright) на ширине телефона и компьютера: три исхода проверки, низкая точность с подтверждением, отправка в ТОиР, окно страницы, плашки, восстановление диалога |

Журналы и отчёты пишутся в `logs/` (вне репозитория).
